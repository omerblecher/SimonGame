## Spacing Scale

Unchanged from Phase 1. No new spacing tokens.

**Phase 3 addition — banner spacer height (not a spacing token):**

The banner spacer height is a runtime value, not a design token. It is managed
by `useBannerHeight()` and expressed as a CSS `height` inline style, not a
Tailwind spacing class. Values:

| Context | Spacer Height | Source |
|---------|---------------|--------|
| Browser (`!isNativePlatform`) | 0px | useBannerHeight() returns 0 |
| Native — before bannerAdLoaded | 50px | Pre-reserved default (D-02) |
| Native — after bannerAdLoaded | actual px | bannerAdLoaded event height |

The 50px pre-reserve prevents layout shift: game layout shifts once at init
(0 → 50), then may shift fractionally when actual banner height is known. The
actual AdMob standard banner height is 50dp, so the shift after bannerAdLoaded
is typically zero or sub-pixel.

## Color

Unchanged from Phase 1 with one additive requirement:

### Loading State Background (index.html — pre-React render)

**Element:** `<body>` background in `index.html`
**Required value:** `background-color: #0f172a` (Tailwind `slate-900`)
**Why:** Before `main.tsx` resolves (UMP consent + AdMob.initialize() + ReactDOM
render), the device screen shows the bare HTML body. Without this, Android WebView
shows a white flash. `#0f172a` matches the glass-panel secondary color and is
visually close to the page background gradient base (`#020617`, `slate-950`).
The contrast delta between `slate-900` and `slate-950` is not perceptible during
the sub-1-second loading window.

**Implementation:** Add to `index.html` `<body>` tag:
```html
<body style="background-color: #0f172a;">
```

This is a one-line addition. It does NOT change the game's runtime background —
`style.css` applies `bg-slate-950` to `body` which overrides the inline style
once Tailwind loads.

## Banner Spacer Contract

This is the primary new UI element in Phase 3.

### Element Identity

| Property | Value |
|----------|-------|
| Element | `<div>` |
| Location | Bottom of App.tsx JSX, inside the game's outermost container div |
| Purpose | Reserve vertical space equal to banner ad height so pads are never obscured |
| Aria role | none — purely structural, not interactive |

### Sizing

```tsx
// useBannerHeight() return value drives height
const bannerHeight = useBannerHeight(); // 0 in browser, 50 pre-load, actual post-load

<div style={{ height: `${bannerHeight}px` }} aria-hidden="true" />
```

| Attribute | Value | Rationale |
|-----------|-------|-----------|
| `height` | `${bannerHeight}px` inline style | Runtime value; not a Tailwind class |
| `width` | auto (100%) | Fills container width — no explicit width needed |
| `background-color` | transparent / none | Spacer must be invisible — the banner renders in native layer above it |
| `pointer-events` | none (default for a non-interactive div) | Must not intercept touch events |
| `z-index` | not set | Spacer lives in DOM flow, not in stacking context |
| `aria-hidden` | true | No semantic content; screen readers skip it |

### Positioning

The spacer div sits at the bottom of the flex column that forms the game layout.
It must be the last child of the outermost container — below all game UI content
including the sidebar/stats panel. It must NOT be placed inside any scrollable
container, fixed-position wrapper, or nested flex child.

**Constraint from ADM-06:** Minimum 50dp gap between banner and nearest interactive
element. The 50px pre-reserve satisfies this before any banner loads. The `bannerAdLoaded`
actual height maintains it after load.

### Layout Interaction

The spacer participates in normal document flow. It pushes game content upward by
its height. The overall page layout is:

```
[game container — flex column, min-h-screen]
  [header / stats row]
  [game board — Simon pads + center disc]
  [sidebar / info cards]
  [banner spacer div — height: bannerHeight px]   ← Phase 3 addition
```

The game container must have `pb-0` or no bottom padding after this change —
the spacer is the sole source of bottom clearance on native.

## GDPR / UMP Consent Dialog

The consent dialog is a native Android UI element rendered by the Google UMP SDK.
It is NOT a React component. There is no custom styling.

| Property | Value |
|----------|-------|
| Dialog type | Native Android (Google User Messaging Platform SDK) |
| Styling | System-default / Google-provided — no custom theming |
| Trigger | On first app launch for EEA/UK users; auto-skipped for non-EEA users |
| Timing | Runs BEFORE ReactDOM.createRoot().render() — React is not mounted yet |
| Loading state | Blank body with background-color #0f172a (see Color section above) |

No UMP-related copy, colors, buttons, or layout changes belong to this React
codebase. The UMP dialog is entirely out of scope for React UI specification.

## App State Transitions (Banner Visibility)

These are native-layer transitions, not React UI state changes. Documented for
executor completeness.

| App State | Banner Behavior | Implementation |
|-----------|-----------------|----------------|
| Foreground (active) | Banner visible | showBanner() called on appStateChange active |
| Background (paused) | Banner hidden | hideBanner() called on appStateChange inactive |

The banner spacer height does NOT change when the banner hides — spacer stays at
its last-known height to prevent layout shift when the app returns to foreground.
This is intentional: a sudden layout re-collapse when backgrounding would be
jarring and unnecessary.

## Loading State Summary

| Loading Phase | What User Sees | Duration |
|---------------|----------------|----------|
| Before UMP SDK runs | Blank screen, `#0f172a` background | ~0ms |
| UMP SDK check (non-EEA) | Blank screen, `#0f172a` background | < 500ms |
| UMP consent dialog (EEA only) | Native Android dialog, no custom UI | User-driven |
| AdMob.initialize() | Blank screen, `#0f172a` background | < 200ms |
| ReactDOM.render() | Game UI appears | Instant |

The total pre-render wait is typically under 1 second on a connected device.
Graceful degradation: if UMP or AdMob.initialize() throws, the catch block calls
ReactDOM.createRoot().render() anyway — the game always renders.
